YANG-Push on-change test case · IETF 127 capture

Where the edit value starts

A router sends a YANG Patch edit with a target and a value. Two things decide whether the value validates: where in the data tree you read it from, and which YANG library builds the schema. The captured value passes only when both are right.

The edit

One captured push-change-update

Subscription 11, a Huawei NE8000, shortened. The target names one list entry. The value is that list entry, with no module prefix.

"target": "/ietf-interfaces:interfaces/interface[name=100GE0/1/2]",
"value": {
  "interface": [ {
    "name": "100GE0/1/2",
    "type": "iana-if-type:ethernetCsmacd",
    "enabled": true,
    "oper-status": "down",
    ...
  } ]
}
Question 1

Read the value from where?

The value is an instance of the target node. So it belongs under the target's parent, which the anydata validation draft calls the anchor. Tools today read it from the schema root instead.

From the schema root, as today

/start
interface ?

Fails. At the root, a member name must carry its module: ietf-interfaces:interface. The draft treats this as an error too.

From the anchor, the target's parent

/
ietf-interfaces:interfacesanchor
interface [name=100GE0/1/2]

Fits. interface is in the anchor's module, so the plain name is the correct form (draft section 4.3.2).

Question 2

Which YANG library builds the schema?

The value uses the identity iana-if-type:ethernetCsmacd. The router published two libraries, and they disagree about iana-if-type. libyang does not resolve an identity from a module that is only imported.

2300156437, the one the message names

  • ietf-interfacesimplemented
  • ietf-yang-typesimport-only
  • iana-if-typeimport-only

Identity not found.

2338653103, published with the capture

  • ietf-interfacesimplemented
  • ietf-yang-typesimport-only
  • iana-if-typeimplemented

Identity resolves.

Answer

The payload we propose should pass

The captured value, unchanged, read from /ietf-interfaces:interfaces. That is check B.

A against B answers the on-change question: read the value from the parent of the target. B against C is the periodic-update problem in the same message. The two problems are separate, but this one payload needs both solved.

Run it

Reproduce the three checks

With mise on macOS. libyang comes from Homebrew, mise sets up Python and a virtual env.

brew install libyang
mise trust && mise install
mise run validate

With Docker on any system. run.sh builds an image that compiles libyang from its release tag, then runs validate.py in it. The first build takes a few minutes.

./run.sh

Without the script, the same two steps by hand:

docker build -t on-change-case .
docker run --rm -v "$PWD":/case:ro on-change-case

Strict, parse-only parsing with libyang 6.4.13 and its Python binding 5.1.0. Names, types and identities are checked. Mandatory nodes and leafref targets are not.

Rule: draft-netana-netmod-yang-anydata-validation-00, sections 3.3 and 4.3.2. Libraries: the router's two published libraries, 2300156437 (named by the message, IETF 126 folder) and 2338653103 (IETF 127 folder), cut to the four modules this value needs. Hostnames in the capture are replaced.
